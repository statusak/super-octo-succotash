# Event Manager: распределённая система управления мероприятиями и бронированиями

## О проекте

Event Manager — распределённая система на стеке .NET 10 + PostgreSQL + Kafka для управления мероприятиями, учётными записями и обработкой бронирований. Архитектура построена по принципам Clean Architecture в каждом микросервисе с разделением на слои Domain, Application, Infrastructure, Presentation.

Система реализует:
- RESTful API с авторизацией через JWT и документацией Swagger;
- управление мероприятиями (создание, фильтрация, пагинация, резервирование мест);
- обработку бронирований с асинхронной фоновой обработкой и защитой от состояний гонки;
- разграничение прав (Admin/User) и глобальную обработку ошибок по RFC 7807;
- асинхронную коммуникацию между сервисами через Kafka (событийная модель).

## Состав системы

| Сервис | Назначение |
| --- | --- |
| `Identity.Service` | Управление учётными записями, авторизация, генерация JWT-токенов |
| `Events.Service` | Управление мероприятиями: создание, фильтрация, резервирование/освобождение мест |
| `Bookings.Service` | Обработка бронирований: создание, фоновая обработка, публикация событий в Kafka |

Все сервисы используют Kafka как шину событий. Конфигурация Kafka вынесена в `docker-compose.yaml`.

## Поток данных и взаимодействие сервисов

### Основные события Kafka

Определены в контрактах (`CSCourse.Contracts.Kafka`):

- `booking.created` — публикуется `Bookings.Service` при создании бронирования со статусом `Pending`.
- `booking.response` — публикуется `Bookings.Service` после завершения обработки (статус `Confirmed`/`Rejected`).
- `booking.cancellation` — публикуется при отмене бронирования.

### Сценарии взаимодействия

1. **Создание бронирования**
   - Пользователь вызывает `POST /events/{eventId}/book` в `Events.Service`.
   - `Events.Service` проверяет наличие мероприятия и доступные места.
   - При успехе `Events.Service` отправляет запрос в `Bookings.Service` (через HTTP или внутреннюю шину, в зависимости от реализации).
   - `Bookings.Service`:
     - создаёт запись бронирования со статусом `Pending`;
     - публикует событие `booking.created` в Kafka;
     - возвращает ответ `202 Accepted`.
   - Фоновый сервис `BookingBackgroundService` периодически опрашивает ожидающие брони (`Pending`) и имитирует обработку (задержка 2 с).
   - После обработки статус меняется на `Confirmed` или `Rejected`, и публикуется событие `booking.response`.

2. **Отмена бронирования**
   - Пользователь или администратор вызывает отмену.
   - `Bookings.Service` обновляет статус, публикует `booking.cancellation`.
   - Другие сервисы могут реагировать на отмену (например, освободить места в `Events.Service`).

3. **Реакция на события**
   - В текущей реализации `Events.Service` и `Identity.Service` подписаны на соответствующие топики Kafka (или будут подписаны в будущем).
   - При получении `booking.response`:
     - `Events.Service` может обновить счётчики занятых мест, если это не сделано атомарно при обработке.
   - При получении `booking.cancellation`:
     - `Events.Service` освобождает места, если они были зарезервированы.

4. **Обработка ошибок и отмена**
   - Если обработка бронирования завершается ошибкой, статус устанавливается в `Rejected`, публикуется `booking.response` с признаком ошибки.
   - Все операции выполняются в транзакциях с уровнем изоляции `RepeatableRead`, используются семафоры и блокировки (`UPDLOCK`) для защиты от состояний гонки.

## Стратегия кеширования

### Используемое решение

Кеширование реализовано на базе **Redis** и применяется в `Events.Service` — сервисе с наиболее частыми операциями чтения (просмотр мероприятий, фильтрация, пагинация). В качестве клиента используется библиотека `StackExchange.Redis`.

### Паттерн — Cache-Aside (Lazy Loading)

Принцип работы:

1. При запросе данных сервис сначала обращается к Redis.
2. Если данные найдены в кеше (cache hit) — возвращаются напрямую из Redis, без обращения к БД.
3. Если данных нет (cache miss) — выполняется запрос к PostgreSQL, результат сохраняется в Redis с заданным TTL, затем возвращается вызывающей стороне.

Этот паттерн выбран потому, что:
- данные мероприятий изменяются относительно редко, а читаются часто;
- он минимизирует нагрузку на PostgreSQL при повторяющихся запросах одних и тех же мероприятий;
- он прост в реализации и не требует изменения логики записи в БД — кеш заполняется «по требованию».

### Кешируемые данные и TTL

| Ключ в Redis | Что кешируется | TTL | Обоснование |
| --- | --- | --- | --- |
| `event:{id}` | Полная сущность мероприятия по идентификатору | 10 минут | Мероприятия редактируются редко; 10 минут — баланс между актуальностью и эффективностью кеша при высоком трафике чтения |
| `events:top10` | Топ-10 мероприятий по заполняемости | 1 минута | Популярность меняется динамически (новые брони поступают часто), поэтому короткий TTL предотвращает отдачу устаревшего рейтинга |

### Инвалидация кеша

Кеш инвалидируется при операциях модификации данных:

- **Обновление мероприятия** (`UpdateAsync`) — удаляются ключ `event:{id}` и ключ `events:top10`, так как изменение может повлиять на топ-10.
- **Удаление мероприятия** (`DeleteEventAsync`) — удаляются ключ `event:{id}` и ключ `events:top10`.
- **События Kafka** (`booking.created`, `booking.cancellation`) — фоновой сервис `EventBackgroundService` при обработке бронирования или отмены удаляет кеш мероприятия по идентификатору, так как изменяются счётчики занятых и доступных мест.

Используется **активная инвалидация** (явное удаление ключей) в сочетании с **TTL как подстраховкой**. Это гарантирует, что даже если явная инвалидация не сработает (например, Redis временно недоступен), данные обновятся по истечении TTL.

### Обработка ошибок Redis

Все обращения к Redis обёрнуты в `try-catch` с перехватом `RedisException`:

- При ошибке **чтения** — логируется предупреждение, запрос падает в основной репозиторий (БД). Пользователь получает корректный ответ, но без кеша.
- При ошибке **записи** — логируется ошибка, но исключение не пробрасывается наружу. Данные корректно возвращаются вызывающей стороне; кеш просто не заполнен.

Это означает, что Redis является **необязательной зависимостью** для корректной работы: при его недоступности система деградирует до прямых запросов к БД без ошибок для пользователя.

### Параметры подключения

Конфигурация Redis вынесена в `RedisSettings` и считывается из секции `Redis` в `appsettings.json`:

| Параметр | Значение по умолчанию | Описание |
| --- | --- | --- |
| `Servers` | `localhost:6379` | Адрес Redis-сервера |
| `Password` | — | Пароль (если требуется) |
| `ConnectTimeout` | 5000 мс | Таймаут подключения |
| `SyncTimeout` | 3000 мс | Таймаут синхронных операций |
| `AbortOnConnectFail` | `false` | Не прерывать запуск сервиса при недоступности Redis |
| `ExpiryEventByIdMinutes` | 10 | TTL кеша мероприятия по ID (минуты) |
| `ExpiryTop10EventsMinutes` | 1 | TTL кеша топ-10 (минуты) |

В `docker-compose.yaml` Redis поднимается как отдельный контейнер (`redis:7.2-alpine`) с healthcheck, а сервисы подключаются к нему по имени хоста `redis:6379`.

### Тестирование

Кеш покрыт unit-тестами (`CacheUnitTests`) с использованием NSubstitute для мокирования `IDatabase` (Redis) и `IEventRepository`. Тесты проверяют:

- попадание в кеш (возврат из Redis без обращения к БД);
- промах кеша (запрос в БД и сохранение в кеш);
- промах при отсутствии данных в БД (кеширование не выполняется);
- инвалидацию кеша при обновлении и удалении;
- отсутствие инвалидации при неуспешном обновлении в БД.

#### Запуск тестирования

```bash
dotnet dotnet test Tests/Unit/Tests.Unit.csproj
```
